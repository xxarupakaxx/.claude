# Plan–Do–Check–Act（PDCA）

`/plan-do-check-act [改善目標]` で、改善を一回の作業で終わらせず、ベースラインと結果を比べて次のサイクルへつなぐ。`GOAL` は改善したい結果、`CYCLE_NUMBER` は任意のサイクル番号（既定 `1`）である。目標が空なら先に確認する。

## サイクル

### Plan

- 問題または望む状態を、対象と範囲付きで定義する。
- 現状の測定値、測定期間、データ源を記録する。未計測は推測で埋めない。
- 必要なら `/why` または `/cause-and-effect` で原因候補を分ける。
- 「Xを変えるとYが改善する」という仮説、変更範囲、成功・失敗の判定、観測期間を決める。
- 変更を戻せる条件と、影響を抑える最小の実験単位を定める。

### Do

計画した範囲だけを実行し、実際に変えたもの、計画からの差、観測した副作用、収集したデータを記録する。実装・設定変更・標準化は、依頼と上位の write scope が許す場合だけ行う。

### Check

- 同じ測定方法で結果を取り、ベースラインと比較する。
- 成功基準を満たしたか、仮説を支持するか、関連する回帰や測定誤差がないかを確認する。
- 成功、失敗、部分成功、判定不能を区別し、対象外の指標を成功の根拠にしない。

### Act

- **成功**：変更を標準化し、必要な文書・監視・回帰チェックを更新する。
- **部分成功**：効果のあった部分を残し、未達の原因に絞って次の仮説を立てる。
- **失敗**：原因と学びを記録し、変更を戻すか、制約を見直して新しいサイクルを設計する。
- **判定不能**：先に測定方法、期間、または不足する証拠を整える。

標準化や次のサイクルを、結果の記録より先に完了扱いにしない。安全性、互換性、コスト、ユーザー影響が成功基準に関係するなら、性能だけで成功としない。

## 出力

各サイクルを次の形で短く残す。

```text
Cycle: <番号>
Goal: <対象と望む結果>
Baseline: <値、期間、出典。未計測なら明記>
Hypothesis: <変更 X が結果 Y に与える予測>
Change: <実際に行ったことと差分>
Success checks: <判定条件と観測期間>
Result: <成功 / 部分成功 / 失敗 / 判定不能。比較値を含む>
Learning: <仮説を支持・反証した証拠と副作用>
Act: <標準化、復旧、または次の仮説>
```

数値は実測値と予測値を分け、サンプル数・期間・測定方法を添える。検証できない改善は Done と言わず、次に必要なチェックを示す。変更の実装、コミット、公開は別の承認済み workflow に委ねる。

# UI 変更時の fresh review

UI の新規画面・コンポーネント追加、またはユーザーが観察できる挙動（状態遷移、インタラクション、レイアウト構造）を変える実装のまとまりを終えたら、実装者とは独立した、まっさらな文脈の通常エージェントに UI/UX レビューを依頼する。変更のまとまりごとに1回でよく、コミットごとには不要である。

余白・色・既存文言の微修正、プロップの引き回し、一括リネーム、i18nキー抽出など、ユーザーが観察できる挙動やレイアウト構造を変えない変更は対象外とする。画面表示文言の品質確認は、プロジェクト固有の文言ルールまたは検証に従う。

## 依頼するレビュー

実装したエージェント自身の文脈でセルフレビューをしない。現在の実行環境で利用でき、上位の指示にも反しない場合に、通常エージェントを会話履歴を引き継がない別セッションとして起動し、次を渡してレビューさせる。Codexでは独立エージェントの`fork_turns`を`none`にし、Claude Codeでは`general-purpose`のAgentを使う。どちらもレビュー依頼に必要な情報だけをpromptで渡す。

- 変更ファイルの一覧。関連ファイルの探索は、変更ファイルが直接 import するものまでを目安にする。
- 取得できる場合のみ、最終変更後の実機スクリーンショットを最大3状態。初期表示と主要操作後を優先する。撮影のためだけにローカル環境を修復しない。
- 画面の目的を1〜3行で説明する。

レビュー依頼には、プロジェクトのデザイン正典、Skill、過去のレビュー結果を追加で渡さない。レビュー担当には、対象コードとスクリーンショットを自由に観察させる。プロジェクトの常時適用ルールが自動的に渡ることまでは防げない。

次の依頼文を必要に応じて使う。

> 対象コード（{ファイルパス}）と添付スクリーンショットの UI/UX をレビューし、問題点を重要度順に最大10件報告してください。各指摘に重要度を付けてください（高=状態の誤伝達・挙動と表示の乖離 / 中=レイアウト挙動・導線・クラッシュリスク / 低=体裁・微視覚）。各指摘には根拠（file:line、またはどのスクリーンショットのどこで観察できるか）を付けてください。関連ファイルの探索は対象コードが直接 import しているものまでにとどめてください。プロジェクトのデザイン文書・design skill・過去のレビュー結果は参照しないでください。サブエージェントの追加起動・skill の実行はしないでください。コントラスト・フォーカス可視性などのアクセシビリティも確認してください。静止画から動き・遷移は評価せず、推測は推測と明記してください。

現在の実行環境に独立したエージェントを起動する機能がない、または上位の指示で委譲できない場合は、fresh review は未実施として理由を報告する。実装者自身のセルフレビューで代替しない。

## レビュー後

各指摘の根拠を確認してから結果に列挙する。根拠が反証された指摘は除外し、その理由を残す。レビューで見つかった問題を修正するかは、ユーザーの指示に従う。修正によって新しいユーザー観察可能な挙動を追加・変更したときだけ、fresh review を再実行する。

このルールは外部サービスへの投稿、コミット、push、PR作成・更新を要求も許可もしない。

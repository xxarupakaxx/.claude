# source-command-tdd

## Red–Green–Refactor

1. **Red**：要件から最小の失敗テストを先に書き、実行して想定した失敗を確認する。成功・境界・エラーのうち、今回の契約に関係するケースを選ぶ。
2. **Green**：そのテストを通す最小の実装を行い、関連する既存テストも実行する。不要な仕様や先回りの抽象化を足さない。
3. **Refactor**：テストが緑のまま重複、命名、構造を整理する。各段階で、次の要件へ進む前に回帰を確認する。

## テスト範囲

機能の境界に応じて選ぶ。関数・状態変換には unit、コンポーネント間やデータフローには integration、UIや公開 API の主要な利用経路には E2E を使う。すべてのレベルを機械的に追加せず、必要な成功・失敗・境界ケースを理由付きでカバーする。カバレッジ率はプロジェクトの既存基準に従い、固定の数値を合格条件にしない。

外部依存はテストダブルを使える範囲で分離し、テスト間の状態共有、`skip`、`only`、検証を弱める fixture をコミットしない。実装の前にテストを追加できない場合は、その制約と代替の検証を報告する。

## 実行

1. リポジトリの README、CLAUDE.md、テスト設定を読み、既存の command と fixture を確認する。
2. フレームワークを検出する（`vitest` / `jest` / `pytest` / `go test` など）。新しい command を推測せず、定義済みの最小 command を使う。
3. Red、Green、Refactor の各結果と変更範囲を記録する。
4. 最後に対象テスト、関連回帰、必要なら型・lintを再実行し、未実行と失敗を隠さず報告する。

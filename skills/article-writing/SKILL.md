# Article Writing

長文の内容を、読者が追える構造と著者の声を保った完成原稿にする。技術文書のMarkdown整形だけなら別スキルへ渡す。

## トリガー

- 「技術記事を書いて」「ブログポストを作って」「設計ドキュメントを書いて」
- `/article <トピック>`

## 進め方

1. 依頼、既存原稿、プロジェクト文書から、topic、読者、目的、長さ、voice、参照source、保存先を確認する。結果が大きく変わる不明点だけ質問する。
2. 目的と素材から主メッセージを一文にし、文書種別に応じた見出しのskeletonを作る。構成が未確定なら先に提示し、指定済みなら執筆へ進む。見本にない体験、数値、引用、人物、場面は創作しない。
3. 各sectionを一律の長さにせず、重要度に応じて濃淡を付ける。事実、推測、未確認を分け、専門語は初出で説明する。既存の自然な文は必要がなければ変えない。
4. 技術記事でコードが必要なら、説明に必要な最小例だけを含める。実行確認済みか未検証かを明記し、未検証コードを動作保証として出さない。
5. タイトル、導入、リンク、参照、誤字を確認し、最後に全文を通読する。日本語の自然さを主目的にする場合は `natural-japanese` へ渡す。

## 種別ごとの骨格（必要な場合だけ）

- tutorial: 導入 → 前提 → 手順 → 完成例 → troubleshooting → 次の一歩
- design: 背景 → 要件 → design → alternatives → decision → impact
- postmortem: 概要 → timeline → root cause → response → prevention

骨格をそのまま埋めるのではなく、主メッセージが伝わる見出しへ置き換える。

## 保存と境界

既定の保存先は `${MEMORY_DIR}/memory/`。ユーザーが場所を指定したらそこへ保存する。コードrepositoryへ文書を置く、既存文書を大きく書き換える、外部へ公開する場合はその範囲を明示して承認を確認する。画像生成は行わず、必要なら別ツールへ依頼する。

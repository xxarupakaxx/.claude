# /vault-metadata-migrator — 既存ノートへのメタデータ遡及付与

> **スコープ**: このスキルは Obsidian Vault（`~/Notes/Vault`）でのみ有効。Vault 外のプロジェクトでは起動しない（`Daily/`、`Inbox/`、`Claude-note/` が存在せず、参照する絶対ルールと拡張フィールドの定義も Vault の `CLAUDE.md` にしかないため）。Vault 内には project scope の同名スキルがあり、そちらが優先される。

新規ノートは `templates/` とスキャン系スキルが新スキーマ（CLAUDE.md「セカンドブレイン拡張フィールド」）を埋めるが、過去の蓄積は空のままである。
このスキルは既存ノートへ `summary` / `related` / `depth` を少しずつ付与し、AIが本文を開かずにVaultを読める状態へ移行する。
**まず `CLAUDE.md` を読み、絶対ルールと拡張フィールドの定義に従うこと。**

frontmatterの一括機械編集はYAML破損の主要リスクなので、次の3つを必ず守る。

1. **バッチ制**: 1回につき10〜20本。全件一括は禁止。
2. **承認制**: 適用前に「ノート / summary案 / depth / related案 / type変更の有無」の一覧を提示し、人間の承認を得る。
3. **挿入のみ**: YAMLの再シリアライズ（読み込み→dump）はしない。既存frontmatterのテキストは一切変更せず、閉じ `---` の直前に新フィールド行を**テキスト挿入**する。

## 1. 現行対象とバッチ計画

過去に作った「knowledge 65本」のバッチ表や完了記録は履歴であり、現行の対象、未処理件数、開始点として再利用しない。起動時に `Inbox/knowledge/**/*.md` を再走査し、現在のfrontmatterから不足fieldを数え直して、その結果だけで今回の候補を決める。

1回につき10〜20本まで、path順など再現可能な順序で対象を固定する。各ノートは `summary`、`related`、`depth`、必要な場合だけ `as_of`、およびtype変更の要否を**field単位**で判定し、summaryが存在するだけでノート全体をskipしない。不足がないノートは対象外として記録する。

候補一覧にはノートごとに、不足field、提案する値、本文の根拠、relatedのリンク先、type変更の有無、既存承認範囲との関係を載せる。過去計画に書かれた件数や分類を現行計画へ戻さない。

## 2. 提案の作り方

- **summary**: 本文の「一文定義」「概要」「冒頭段落」から1行に要約する。本文にない主張を足さない。`: ` を含みやすいので必ず `"..."` で囲む。既存summaryは変更候補にしない。
- **depth**: `flash`（速報由来）/ `overview`（単発理解）/ `systematic`（合格基準つき体系学習）。迷ったら overview。
- **related**: 実在ノートへの `"[[リンク]]"` を2〜4本。ハブ優先（所属MOC、正本ノート）+ 本文の「🔗 関連」節にある強い関連。無理に作らない。
- **as_of**: 時間で変わる情報を含むのに無い場合だけ提案する（既にある場合は触らない）。
- **type統一**: `type: note` → `type: knowledge` は**値の変更**なので、フィールド追加とは分けて承認を取る。個人的な雑記・思考メモは knowledge にしない。

既存の承認が同じbatch・同じfield追加・同じ対象範囲を含む場合、変更していないfieldや対象へ一律に再承認を求めない。type変更、対象範囲の拡大、本文変更、既存値の変更は別の承認として扱う。

## 3. 適用の手順（承認後）

Pythonスクリプトで1ファイルずつ処理する。

1. 各ファイルの作業直前に、現在のstatusと未コミット差分を確認する。原文の退避が必要な場合だけ、Vault外かつGit・同期対象外のowner-only一時ディレクトリ（dir `700`）とファイル（mode `600`）を自分で作成し、原文バイト列とSHA-256をそこへ保存する。原文にsecretや機微値が含まれると分かった資料は退避・加工せず、安全な取扱いを確認して停止する。task logへ原文をコピーせず、path・hash・statusだけを記録する。GitのHEADや全体restoreを復元元にしない。
2. 適用前の frontmatter を `yaml.safe_load` でパースして退避（d0）。
3. 閉じ `---` の直前に新フィールド行を挿入（type変更が承認された場合のみ `type:` 行を置換）。本文には触らない。
4. 適用後を再パース（d1）し、次を検証する。失敗したら作業直前に自分が作成したowner-only退避のバイト列だけでそのファイルを復元し、復元後のhashを照合して報告する。`git restore` で作業前のdirtyを上書きしない。検証に成功し、復元を行った場合は復元の成功を確認した後、退避を除去する場合も自分が作成した一時コピーだけを適切に除去し、原本は削除しない。
   - d1 がパース可能
   - 既存キーの値が不変（d0 の全キーで d1 と一致。type変更承認時の type のみ例外）
   - 新キー（summary / depth / related）が存在し、related の各要素が `[[...]]` 形式
5. バッチ全体で `git diff --numstat` を取り、挿入行数が期待どおりで、削除行が type 変更分（承認時のみ）に限られることを確認する。
6. related に書いたリンク先が実在することを確認する（ファイル名ベース）。

PyYAMLでd0/d1の意味検証ができない場合、構造確認だけではYAML全体の安全性を証明できない。`structural-only` と明記し、意味検証済み・全件移行済みとは報告しない。意味検証が必要な次batchへ進まず、再開条件（parserの利用または人間確認）を残す。

## 4. 報告

適用本数、field単位の不足数、対象外・スキップ本数、検証レベル（YAML意味検証 / structural-only / 未実行）、git diffのサマリ、次batchの候補を短く返す。候補数や次batchは起動時の現行再走査から算出し、旧65本の計画へ戻さない。
コミットとpushは指示があった場合のみ行う（通常はobsidian-gitに委ねる）。

## ガード

- `Claude-note/` は対象外（読みもしない）。
- リネーム・削除・本文変更はしない。frontmatterへの**行挿入**と、承認された `type:` 行の置換のみ。
- 1バッチでも検証に失敗したファイルがあれば、次バッチへ進む前に原因を報告する。
- 実行環境に PyYAML が無い場合は、構造チェック（`---` 対応、インデント、`: ` の引用）に切り替え、その旨を報告する。

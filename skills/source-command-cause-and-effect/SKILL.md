# source-command-cause-and-effect

`/cause-and-effect [問題の説明]` で、症状の原因候補を **人、プロセス、技術、環境、方法、材料** の六分類に分けて調べる。`PROBLEM` は問題、`CATEGORIES` は対象カテゴリ（既定は全六分類）である。分類は探索の枠であり、すべてのカテゴリに原因があると決めつけない。

## 手順

1. 問題を観測事実、範囲、時点、影響とともに一文で固定する。
2. 各カテゴリで、コード、設定、ログ、手順、データ、関係者など確認できる原因候補を挙げる。
3. 候補ごとに「なぜ」を掘り、直接原因、寄与要因、根本原因、仮説を区別する。必要なら `/why` へ分岐する。
4. 複数カテゴリにまたがる原因を関連付け、証拠がない候補は `未確認` とする。
5. 影響、起こりやすさ、実現可能性、工数を根拠付きで比較し、優先順位を決める。推測の数値を測定結果として扱わない。
6. 上位候補に対する対策、検証方法、再発監視を提案する。実装や外部変更は別の承認済み作業に渡す。

## カテゴリの視点

- **人**：技能、役割、コミュニケーション、引き継ぎ
- **プロセス**：要件、レビュー、標準、承認、検証
- **技術**：コード、ツール、インフラ、依存、設定
- **環境**：実行環境、デプロイ先、ネットワーク、外部条件
- **方法**：設計、アーキテクチャ、作業手順、運用パターン
- **材料**：入力データ、fixture、サードパーティ、利用可能な資源

## 出力

```text
問題: <観測された症状と影響>
スコープ / 証拠: <調べた範囲と参照>
人: <候補> — <根拠 / 未確認>
プロセス: <候補> — <根拠 / 未確認>
技術: <候補> — <根拠 / 未確認>
環境: <候補> — <根拠 / 未確認>
方法: <候補> — <根拠 / 未確認>
材料: <候補> — <根拠 / 未確認>
根本原因候補: <確度、因果のつながり>
優先順位: <影響・可能性・実現可能性・工数の理由>
次の確認 / 対策: <合格条件と再発監視>
```

根本原因を一つに絞れない場合は、反証に必要な追加観測を残す。広い工程改善は `/analyse`、反復実験は `/plan-do-check-act` と組み合わせる。

# カイゼン

一度に扱う変更を小さくし、各段階を検証してから次へ進めるための判断レンズ。目的は完璧さではなく、品質と単純さを壊さず改善を積み重ねること。

## 適用境界

このSkillは、カイゼン・継続的改善を明示されたとき、または承認済み変更へ改善方針を適用するときだけ使う。通常の新規実装や単発bugfixの主routeにはせず、implementing-workやtddなど対象に合うSkillへ渡す。

## 4つの柱

### 1. 継続的改善

- 現在の依頼を満たす最小の変更から始める。
- 一度に一つの改善を加え、各段階でtest・lint・実行確認を行う。
- 既存作業の範囲にある小さな問題は候補にするが、scopeを勝手に広げない。
- 「十分良い」時点で止め、限界効用の低い大改修を避ける。

### 2. ポカヨケ（エラー防止）

実行時の注意だけに頼らず、設計・型・コンパイル時に不正な状態を表しにくくする。

1. 型システムで契約を表す。
2. システム境界で入力を一度検証し、検証済み型として渡す。
3. 事前条件とguardで早く明確に失敗する。
4. error boundaryや段階的劣化で予期せぬ失敗を隔離する。

エラーメッセージは原因と次の行動が分かるものにする。設定不足は危険な既定値で隠さず、可能なら起動時に検出する。

### 3. 標準化

既存codebaseの解決済みパターン、命名、layer/module境界を先に調べる。新しい抽象化は明確な利得と合意がある場合だけ導入する。READMEは導入・利用、AI向け指示は正本のルール、コメントは「何を」より「なぜ」を説明し、linter・typecheck・test・CIを品質gateとして利用する。

### 4. JIT / YAGNI

- 今の要件に必要なものだけ実装する。
- 「将来必要かも」のAPI、設定、抽象化を先回りして増やさない。
- 最適化前に測定し、profileと成功基準で効果を確かめる。
- 早すぎる最適化や大規模リファクタを小さな改善と呼ばない。

## 適用の仕方

- **機能実装**: 最小の動作を作り、必要なvalidation/error handlingを一つ加え、testで確認する。
- **リファクタ**: 一つのcode smellまたは一つの境界を対象にし、各段階でテストを通す。
- **設計**: 要件と既存の制約を根拠に、単純な案から比較する。性能改善はprofileを先に取る。
- **レビュー**: 致命的、重要、改善推奨の順に、実害と根拠を添えて提案する。

変更によって別の改善が見つかっても、依頼範囲を超えるものは別候補として分ける。例を確認したいときだけ `references/examples.md` の該当セクションを読む。

## 完了条件

- 各変更の目的と範囲が明確である。
- 不正入力・不正状態・設定不足の検出位置が適切である。
- 既存パターンに沿い、不要な抽象化や未使用機能を追加していない。
- 変更ごとの検証が通り、次の改善を続けるか止める判断が説明できる。

# 周辺コンテキストの調査先ガイド

URLから「何を追加調査すべきか」を判断するための指針。

## URLの種類別 調査パターン

### GitHub リポジトリ（github.com/user/repo）

優先順位順に以下を調査する。取得できたものだけでよい。

1. **README.md** — プロジェクト全体の概要と動機
2. **SPEC.md / spec/ ディレクトリ** — 仕様書（あれば最重要）
3. **docs/ ディレクトリ** — 詳細ドキュメント
4. **主要なソースファイル** — コアロジックの実装（実装の「なぜ」を理解するため）

rawコンテンツのURLパターン：
```
github.com/user/repo/blob/main/path.md
→ raw.githubusercontent.com/user/repo/main/path.md
```

### 技術ブログ・解説記事

記事の本文から以下を特定して追加調査する：
- 言及されているGitHubリポジトリ
- 引用されている公式ドキュメント
- 比較・対比されている技術名（→ その技術の公式ドキュメント or GitHub）

### 公式ドキュメント（docs.xxx.com 等）

- **Overview/Getting Started** — 設計思想と基本概念
- **Architecture / Design** — 内部構造
- **Changelog / Release Notes** — 何が変わってきたか（設計の変遷）
- **FAQ / Troubleshooting** — 既知の問題と落とし穴

### 仕様書・RFCクラス

- **リファレンス実装**（仕様書がリポジトリならimplディレクトリ等）
- **GitHub Issues** — 既知の問題・議論中の改善案
- **類似仕様** — 競合する標準との比較

---

## 調査の深さの判断

**1URLだけで完結しそうなとき**：Step 2（本文取得）のみで十分。

**以下のキーワードがある場合は周辺調査を追加**：
- 「仕組みを理解したい」「どう動いているか」
- 「他と何が違うか」「なぜ〜じゃないか」
- 「背景を知りたい」「なぜ作られたか」
- 「深掘り」「詳しく」

**調査対象が複数あるとき**：`research` スキルに調査対象を分けて渡す。
調査結果には、一次情報、公式ドキュメント、仕様、ソースコードを優先し、重要な主張ごとに出典URLを残す。

---

## research への指示テンプレート

```
このドキュメント/リポジトリについて、research スキルのルールで以下の情報を詳細に調査してください：

1. 全体の概要と目的（なぜ存在するか）
2. 技術的な仕組みの詳細（原理・アーキテクチャ・データフロー）
3. 設計上の選択とその理由（なぜこうなっているか）
4. 他技術との比較・位置づけ
5. ユースケースと想定ユーザー
6. 既知の制限・注意点・落とし穴
7. バージョン/ロードマップ情報（あれば）

「10年後の新人でも理解できる」レベルで詳しく。
取得できた情報はできる限り全文を報告してください（要約しすぎない）。
```

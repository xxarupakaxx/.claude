# source-command-why

ユーザーが `/why [問題の説明]` を求めたときに使う。症状への場当たり的な修正で止めず、根拠が続く限り「なぜ」を掘る。

## 入力

- `ISSUE`：分析する問題または症状（未指定なら入力を促す）
- `DEPTH`：目安5。根拠が尽きたら早く止め、5回を埋めるために推測しない。

## 手順

1. 問題を観察可能な症状として書き、発生条件と影響を確認する。
2. 「なぜ起きたか」を問い、回答の根拠（log、test、設定、履歴など）を記録する。
3. 回答ごとに次の「なぜ」を繰り返す。技術原因とプロセス・仕組み・環境の両方を検討する。
4. 複数の原因が現れたら枝を分け、枝ごとに根拠と未確認事項を追う。「人為的ミス」で止めず、なぜそのミスが可能だったかを確認する。
5. 根本原因の候補から症状へ逆方向にたどり、因果がつながるか検証する。
6. 根本原因に対応する対策、検証方法、再発監視を提案する。実装する場合は実装後に症状の解消を確認する。

## 出力

```markdown
問題: <症状>

| 段階 | なぜ | 回答 | 根拠 / 未確認 |
|---|---|---|---|
| 1 | なぜ症状が起きたか | ... | ... |

根本原因候補: ...
逆方向の検証: ...
対策と検証: ...
```

真の根本原因に到達したら止める。原因を断定できない場合は最有力仮説と必要な観測を分けて報告する。

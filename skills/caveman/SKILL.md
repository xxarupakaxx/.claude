# Caveman Mode（原始人モード）

賢さを足すのではなく、対象の目的に必要なものだけを残す局所的な簡素化である。プロジェクト全体への適用や、明示されていない自動発動はしない。

## 対象と原則

ユーザーが指定した関数、ファイル、設計文書、README、コメントだけを扱う。最初に「これは何をするか」を一文で書き、次を基準に削る。

- 名前は短く具体的にし、処理の流れを追いやすくする。
- 小さな対象なら不要な抽象化、階層、ヘルパー、説明コメントを減らす。
- コメントは「なぜ必要か」だけを残す。
- 組み込み機能を優先し、依存追加や先回りの拡張を避ける。
- 早期 return、分岐、型、ログ、エラー処理は、削除すると契約・安全性・可読性を損なうか確認してから変える。短さのために例外処理や境界の検証を捨てない。

## 手順

1. 対象、利用者、公開 API、入出力、エラー時の契約を読む。
2. 意図を一文にし、保持すべき挙動と削ってよい重複を分ける。
3. 最小の変更を一つずつ適用する。引数数、行数、単一戻り値の固定目標は置かない。
4. 呼び出し側、依存、型、ログ、認可、リソース解放への影響を確認する。公開シグネチャ、テスト用の seam、エラー分類は理由なく変えない。
5. 関連する既存テストと、変更で影響を受ける成功・失敗ケースを実行する。失敗や契約の不明点が残るなら元の形を保ち、未確認として報告する。

## 出力と完了

変更前後の意図、削ったもの、保持した契約、検証結果を短く示す。完了条件は、対象の目的を満たし、関連テストが通り、公開 API・安全境界・エラー処理が意図せず変わっていないこと。行数削減は手段であって合格条件ではない。

大規模な構造変更は `improving-architecture`、全体のトレードオフ確認は `zoom-out` に渡す。

# 検証の落とし穴

初めての人向けの解説は、読み手が自分で反証しにくいぶん、書き手の言い過ぎがそのまま判断を誤らせます。次は、この種の解説で起きやすい誤りです。指摘や答えを書く前と、独立レビューを頼むときの観点として使います。

## 主張の立て方

1. **定義と経路を分ける。** 「X の状態なら Y がある」は、定義（コメント、型、遷移表）なのか、そこへ進む経路の結果なのかを分けて書く。経路の結果なら、その経路ができた日付（導入した commit）より前のデータには当てはまらないことがある。
2. **値を書き込む箇所を全部探す。** 代入、遷移関数、SQL の UPDATE を grep で全件挙げてから「ここだけ」と書く。
3. **呼び出し元は、RPC の権限まで確かめる。** 「画面から呼ぶ」と書く前に、proto やルーティングで、システム専用（バッチ）か利用者が呼ぶものかを確かめる。
4. **「止まる」「実行される」は、次の分岐まで追う。** 安全のための確認（承認など）を通った後に何が起きるかを、実際の分岐でたどる（対象が0件なら外部 API を呼ばずに終わる、など）。
5. **PR が新しく起こすことと、前からあることを分ける。** 「PR の前後で何が変わるか」を一文で言えるか確かめる。前からある問題を PR のせいにしない。
6. **エラーやアラートは分岐ごとに違う。** 「同じアラートが鳴る」と書く前に、条件ごとのエラーコードを確かめる。

## 根拠の強さ

7. **CI の名前を根拠にしない。** そのチェックが何を検査するか（構文だけか、実際に実行するか）をソースで読む。
8. **自分で確かめたものだけを「確認済み」にする。** PR 本文に書かれた作者の手元の実行結果や、公式文書の記述は「出典の記載」。
9. **本番のデータは「未確認」と書く。** コードから言えるのは「経路上そうなる」まで。既存データの状態は、確かめる SQL を添えて読み手に渡す。
10. **抜き書きが古くなっていないか確かめる。** merge-base の後に base branch で対象ファイルが変わっていないかを `git diff <merge-base> <base の先端> -- <path>` で見る。変わっていれば、その変更で指摘が崩れないかを確かめ、崩れるなら書き直す。

## 読み手への見せ方

11. **PR 前の挙動には merge-base の抜き書きを使う。** head のコメントは PR 後の挙動を書いているので、PR 前の説明に使うと読み手が混乱する。base branch の先端は分岐後の変更を含むことがあり、PR の差分の行番号と食い違う。
12. **要件の言葉と実装の判定のずれを、用語の約束で固定する**（例: 要件は「0円」、判定は「0件」）。本文で揺らさない。
13. **同じ名前で意味が逆の値に注意する**（例: 親の状態の skipped は正常終了、子の状態の skipped は失敗扱い）。
14. **既存データとリリースの順番を必ず見る。** 新しい状態を足す PR では、前から残っているデータをどう終わらせるか、旧版のアプリやロールバックで新しい値を読めるかを確かめる。migration、アプリ、後続の migration（既存データの書き換えなど）がある場合は、どの順に出せば各時点の組み合わせで壊れないかを、順番として書く。
15. **作者が判断を求めた点をすべて拾う。** PR 本文の「見てほしい観点」に、漏れなく見解を書く。
16. **安全のための確認（承認、権限、お金）を緩める方向に読めるコメントや提案は重く扱う。** 将来の変更者がそれを信じて分岐を足す道筋まで書く。
17. **見え方の変化も影響に数える。** 異常なケースが、正常に終わったように見える状態へ変わるなら、気づく手段（監視、エラーのフラグ）があるかを書く。

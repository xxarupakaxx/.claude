# source-command-plan-do-check-act

ユーザーが `plan-do-check-act` を実行したいときに、改善目標を小さな実験へ分け、結果を測って次のサイクルまたは標準化を判断する。

```text
/plan-do-check-act [改善目標]
```

`GOAL` は改善対象、`CYCLE_NUMBER` はサイクル番号（既定1）。目標、baseline、成功基準が入力から決められない場合は、実験を始めず不足情報を確認する。

## サイクル

### PLAN

- 問題または改善目標と対象範囲を定義する。
- 現状の測定値、再現条件、制約、影響を記録する。
- 根本原因を `/why` または `/cause-and-effect` で調べ、仮説を「Xを変えるとYがどう改善する」と書く。
- 変更範囲を小さく定め、成功指標、測定方法、期間、停止・ロールバック条件を決める。

### DO

- 合意した範囲で変更を実施し、外部writeや本番変更には既存の承認gateを適用する。
- 実施内容、計画との差分、観測値、予期しない結果を記録する。変更を広げる場合は新しい計画として扱う。

### CHECK

- 同じ測定方法で変更後の値を取り、baselineと比較する。
- 仮説、成功基準、想定外の副作用を確認する。
- 成功・失敗・部分成功を、データと不確実性を添えて記録する。

### ACT

- **成功**: 変更を標準化し、必要な文書・チェック・自動化を更新して回帰を監視する。
- **失敗**: 原因と学びを残し、仮説または範囲を修正して次のサイクルを計画する。
- **部分成功**: 効果が確認できた部分だけを標準化し、残課題を次のサイクルへ渡す。

同じ失敗を3サイクル繰り返す場合は、原因分析・目標・測定方法を見直してから続行する。変更を標準化する前に、成功基準、回帰監視、ロールバック手段がそろっていることを確認する。

## 記録テンプレート

```markdown
## PDCA cycle <番号>: <目標>

### PLAN
- 問題 / 対象: ...
- Baseline: ...
- 根拠と根本原因: ...
- 仮説: ...
- 変更: ...
- 成功基準 / 測定 / 期限: ...
- 停止・ロールバック条件: ...

### DO
- 実施したこと: ...
- 計画との差分: ...
- 観測・副作用: ...

### CHECK
- 結果とbaseline比較: ...
- 仮説の判定: confirmed | partial | rejected
- 根拠と未確認事項: ...

### ACT
- 決定: standardize | adjust | next-cycle | stop
- 理由、担当、次の確認: ...
```

主観的な成功宣言だけで完了にしない。包括的な一枚の問題分析が必要なら `/analyse-problem` を使う。

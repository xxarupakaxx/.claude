# Diagnosing Bugs

修正を急がず、まず「失敗と成功を短く判定できる観測ループ」を作る。ループを作れない場合は、その制約と必要な入力を明記してから次の調査を選ぶ。単純に原因が明らかな小さな修正では、不要な段階を増やさない。

## 1. ループを選ぶ

問題の種類に応じて [references/feedback-loop-recipes.md](references/feedback-loop-recipes.md) の該当レシピだけを読む。

| 問題 | まず使う観測 |
|---|---|
| 単体ロジック | failing test |
| HTTP / webhook | curlまたはHTTP probe |
| CLI / script | 固定fixtureと1コマンド |
| UI / E2E | headless browserとスクリーンショット |
| 本番限定 | ログ・traceのreplay（許可されたデータだけ） |
| 入力依存・断続的 | property/fuzzまたはseed固定 |
| 回帰時期が不明 | `git bisect` |
| 既存実装との等価性 | differential test |
| 自動化困難 | ユーザー実行のHITL loop |

ローカルfixture、DB、外部APIなどの状態を可能な限り固定し、成功・失敗をexit code、出力、assertionなどで判定する。30秒以内は目標であり、環境上困難なら最短の再利用可能なループと所要時間を記録する。HITLではユーザーにsecretを貼らせず、必要なログやスクリーンショットの範囲を限定する。

## 2. 再現して境界を狭める

- バグを確実に起こす最小入力をfixtureまたは回帰testとして固定する。断続的な場合はseed、並列度、時刻などを固定する。
- 再現できない場合はログ、stack trace、git history、環境差分を確認し、必要ならユーザーへ再現環境のsnapshotを求める。推測で修正しない。
- 時間、コード、データ、設定の一軸ずつを切り替えて再実行し、観測が変わる境界を特定する。状態遷移は遷移元と補償・期限切れ経路を列挙し、一覧・集約処理は統合入口まで確認する。

追加の一時traceは失敗操作の直前に限定して入れ、ディレクトリ、cwd、入力の識別子、`new Error().stack`など必要な情報だけをstderrへ出す。識別用に`TRACE-DIAGNOSE-XXXX`を付け、修正前後の確認後に必ず削除する。secretや個人情報は記録しない。

## 3. 仮説を検証する

根本原因の仮説は、観測された症状、なぜ今発生したか、修正後に変わる観測を説明できる必要がある。修正前に予測を立て、修正後に同じループで確認する。予測と違えば仮説を捨てて探索へ戻る。症状の箇所だけでなく、無効な値や誤った状態が最初に生じた呼び出し元まで追う。

## 4. 完了と再発防止

- 最小再現を意味のある回帰testへ昇格する。テスト追加が不適切なら、その理由と代替検証を報告する。
- 一時traceが残っていないことを`rg "TRACE-DIAGNOSE" --no-ignore`で確認する。
- 必要な修正を適用し、元のループ、影響する既存test、typecheck/buildなどを実行する。
- 非自明な原因だけを、許可された知識保存先へ要点・再現条件・修正パターンとして残す。

外部サービス、production、認証情報を扱う操作はプロジェクトの承認境界に従う。調査結果では、再現状況、根拠、修正、検証、未確認事項を分けて示す。

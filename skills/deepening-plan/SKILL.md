# Deepening Plan

Phase 2で作成済みの計画を、追加調査で具体化する。調査で方針が変わらない場合は実行しない。計画の方向性を再設計するSkillではない。

## 前提と入力

- `${MEMORY_DIR}/memory/YYMMDD_<task>/30_plan.html` が必要。既存taskでHTMLがない場合だけ、互換入力として`30_plan.md`を読む。
- 計画に複数のtaskまたは、調査で判断が変わり得る技術・外部依存があること。入力を読んで不確実性を列挙し、調査対象を絞る。

## 進め方

1. 計画の各taskから、未確定のlibrary/API、architecture、外部サービス、性能・security上の論点を拾う。すでに確認済みの事実や、計画を変えない一般論は対象外にする。
2. 論点ごとに必要な調査だけを選ぶ。公式ドキュメント・仕様・一次sourceを優先し、Context7（library/API）、deepwiki（対象repositoryの設計）、WebSearch（最新の公式情報）、`learnings-researcher`（過去の`solutions/`・`memories/`）を使う。互いに独立し、かつ実行コストに見合う場合だけ並列に行う。
3. 結果を根拠付きで計画へ反映する。API名や落とし穴を具体化し、必要なら代替案・リスク・検証方法を追加する。推測は「要確認」とし、出典のない数値や方針を補作しない。
4. `05_log.md`へ、追加した根拠、変えた判断、残るリスクを短く追記する。計画の大きな方向転換が必要なら、deepeningで決めずレビューまたはユーザー確認へ戻す。

## 成果物と境界

出力は強化された`30_plan.html`と`05_log.md`である。元HTMLを旧Markdownへ変換したり、実装・レビューを同時に行ったりしない。計画の機械検証、Roadmap同期、ユーザー検証gateは呼出元のworkflowに従う。

調査が失敗しても、同じ失敗を隠すfallbackや未確認情報の断定をしない。Context7などのdocs取得がquotaや環境で失敗した場合は、公式ドキュメントを直接確認できる範囲だけで続け、確認できない論点を残す。

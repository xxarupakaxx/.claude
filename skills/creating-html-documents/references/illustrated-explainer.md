# 初学者向けexplainerの型

前提知識のない読者に一つのドメインを最後まで把握させるための、章立て、アナロジー、絵の型を定める。主に `technical-explainer` の上に重ねる既定であり、ユーザーが「例え話を入れて」「絵にして」と言わなくても適用する。ドメインは問わない。例に決済を使う箇所は、対象で実際に動くもの（認証なら要求・証明・権限、物流なら荷物・伝票）に置き換えて使う。

## 発火条件

読者が対象ドメインの前提知識を持たず、目的がその読者の理解である解説に適用する。次のどちらかを手がかりにする。

- 読者が「前提知識がない」「まっさら」「初めて」と書かれている、または依頼文からそう読める。
- 依頼が「〜とは何か」「ドメインを把握したい」のように対象を一から知りたい形で、読者が実務者だと分かる手がかりがない。

「仕組みを教えて」「解説して」のような依頼語は、読者の理解が目的であることの合図で、`mastery-explainer.md` の既定を発火させる。それだけでは読者を初学者とみなさない。対象の主体や段階の数も判定に使わない。

次には適用しない。

- 読者が実務者（そのドメインの用語と基本の流れを知っている人）の文書。実務者向けの `technical-explainer` や仕様説明も含む。目的が読者の理解なら、`mastery-explainer.md` の既定だけを重ねる。
- `decision-plan`、チームが差分を確かめて判断するためのレビュー記録、`screen-diff`、短い確認用HTML、ダッシュボード。

読者と目的の判断は、迷わなかった場合も `<meta name="reader" content="読者と目的を一文で">` に残す。読者像が曖昧なときは、読者と目的を一文で決めてから残す。

読者自身の理解が目的の文書では、`mastery-explainer.md` の既定も重ねる。この型は前提知識を補い、`mastery-explainer.md` は読者が理解の穴に気づく仕掛けを担う。

## 章立ての既定

全体の順と、理解の確認の既定やファイルの索引と重ねたときの位置は、`document-system.md` のTechnical explainerの【初学者】の項目に従う。ここでは初学者向けで加わる章の中身を、その順に並べる。

- 章を読む順: decision bandの中に入れない。bandの直後、orientationの前に一行で置き（例: 全体像 → 用語 → 1件を追う → 歴史 → 詳細）、各段を該当する章へリンクする。理解の確認の既定を重ねるときは、「読み終えたらできること」の直後に置く。
- 場面の絵と登場人物の地図: orientationの後のoverviewを場面の絵にし、続けて登場人物の地図を置く。描き方と、主体が少ないときの扱いは下の「絵の型」に置く。
- 身近な例で掴む章: 三つ程度の日常の例を並べ、同型であることを絵で示す。
- 最小用語: 定義リスト（`dl`）で並べ、各用語の説明に「場面の絵のどの番号に当たるか」と「なぜこの語が要るか」を含める。
- 代表ケースの時系列: 仮設と明示した数字で、1件が最初から最後まで流れる。
- なぜ生まれたか: 歴史、以前の方法、何を解いたか、何が難しくなったか。昔と今の違いは、下の「昔と今の帯」の絵か、昔と今を左右に並べたカードで見せる。
- 詳細章: 仕組み、対象で動くもの（お金、データ、権限など）と記録の流れ、比較対象、周辺の仕組み。各章に絵を一枚。
- うまくいかないとき: 失敗の入口から終点までを階段で描く。
- 規制・制度: 対象を外から縛る法令、業界の規則、監督があるときだけ章を立て、制度ごとのカードに要点、as of日付、出典を置く。対象そのものを定める仕様や標準は詳細章で扱う。
- 似た言葉の整理。
- 自己テスト: 答えは `details` で折りたたみ、開く前に答えさせる。問いの作り方は `mastery-explainer.md` に従い、理解の確認の既定の自己テストと一つにまとめる。
- 出典: 一次、二次、内部ノート、解釈を区別する。

目次は本文前の左上の折りたたみ欄に置き、初期状態は閉じる。常設の右railは設けない。用語は本文の初出で定義する。参照用の用語集は、読者が知らない専門語が3つ以上の章で繰り返し出るときだけ目次の折りたたみに入れ、その語だけを4行以内の短い定義で載せる。

## アナロジーの規則

- 主要章ごとに `.analogy` の囲みを一つ置く。見出しは「たとえるなら」。
- 囲みの末尾に「比喩の限界」を必ず書く。どこで比喩が崩れ、専門の仕組みが必要になるかを一文で示す。この一文が次の章への導線になる。
- 比喩は読者が全員経験しているものから選ぶ（家計、給料、光熱費、図書館、家賃、貸し傘、商品券など）。業界の別の専門用語で言い換えない。
- 一つの比喩を複数章で再利用してよい。歴史の章で出した具体例（実在の企業や慣行）は、後の章の根拠として繰り返し参照する。
- 比喩のためだけに数字や人物を創作しない。数字を使う場合は「仮設」と明示する。

## 絵の型

各型は一枚のinline SVGで描く。図番号は章番号ベース（第6章の一枚目は図6a）にし、overviewだけ図1、図1b、図1cとする。場面の絵の前にドメイン俯瞰図を置くなら、ドメイン俯瞰図を図1、場面の絵を図1bにする。ドメイン俯瞰図を置いた文書では、登場人物の地図を別に描かず、ドメイン俯瞰図の主体に役割と章番号を書いて代える。各型の名前の後に、答える問いと描くものを書く。

- 場面の絵（scene overview）: 全体で何が誰から誰へ動くかに答える。当事者を建物や人の形で並べ（2者なら左右、3者以上なら流れの順）、対象で実際に動くもの（決済ならモノ・書類・お金、認証なら要求・証明・権限）を種類ごとに上下の段へ分けて矢印で描く。段は実際に動くものの数だけにし、空の段を作らない。各当事者のそばに、それぞれが持つ記録（帳簿、ログ、ログイン状態など）を置き、待つ期間を下段に置く。失敗の行き先は、場面の問いに失敗が含まれるときだけ描き、失敗の入口から終点までは「うまくいかないとき」の章の階段で描く。番号は1から順の丸いバッジにし、意味を図の中の凡例に書いて、本文で再利用する。英字一文字の記号は置かず、範囲や失敗の行き先は「この文書の範囲」「払われない場合」のような語で書く。題材が一つの取引の場面に収まらず、業界全体を見せる必要があるなら、場面の絵の前に `overview-patterns.md` のドメイン俯瞰図を置く。
- 登場人物の地図: 周りに誰がいて、何を手伝うか縛るかに答える。中央に読者が立場を重ねる当事者（読者がどの当事者でもないなら、文書の主題の当事者）、周囲に実在する主体を置き、各箱に役割一文と、担当する番号と章番号を書く。主体が多いときは役割の近いものをまとめて6程度にし、数を合わせるために主体を作らない。周辺の主体がすべて場面の絵に描かれ、地図が場面の絵の繰り返しになるなら、地図を別に描かず、場面の絵の直後の箇条書きで各主体の役割と担当する番号・章番号を示す。
- 同型並列: 身近な例と同じ形かに答える。三つの例を行に並べ、対象の流れと同じ段（決済なら「先に受け取る → 記録して待つ → まとめて払う」）を列に揃える。
- 両端: 二つの用語は同じものかに答える。一本の線の両端にラベルを置き、線が切れる条件を書く。
- 昔と今の帯: 何が変わり、何が変わっていないかに答える。同じ長さの期間の帯を上下に置き、印の数や間隔の違いで見せる。
- ものさし・bar: どこまで許すか、いくらまでかに答える。目盛りと閾値、段階（A〜E）、使用量と上限のbarを描く。
- 資金の穴: いつ出て、いつ戻るかに答える。お金や在庫が先に出て後から戻る対象で使う。時間軸に出金と入金の矢印を置き、その間を帯で塗る。対比として裏返した例を下段に置く。
- 下りの階段: 悪化するとどうなるかに答える。左上から右下へ段を下り、各段に手段と時期を書く。途中で戻れる経路を破線で描く。
- before / afterの帯: 制度や変更で何が消えたかに答える。旧と新の期間の帯を上下に置き、消えた区間を破線枠で示す。

## 描き方の規則

- viewBox幅は図枠の実幅に合わせ、表示倍率（描画幅÷viewBox幅）を0.9以上にする（SKILL.mdの「視覚言語」）。高さは内容で決める。文字は基本20px、補助15px、矢印ラベル14pxを起点にし、表示倍率を掛けた実寸で12px未満にしない。日本語1文字はfont-sizeとほぼ同じ幅で見積もり、箱に入る文字数を先に数える。
- 箱の中の文は2行までにし、長い説明はcaptionか本文へ逃がす。
- 色は本文と同じ3系統だけにする。読者が追う主な流れ（決済ならお金）はaccent、それ以外の動き（品物、書類、要求など）はink、失敗はwarning。色だけに意味を持たせず、実線・破線・ラベルでも区別する。
- アイコンは基本図形（rect、polygon、circle、line）の組み合わせで描く。建物、人、箱、書類、硬貨、鍵、画面、帳簿の程度で十分で、装飾を増やさない。
- 各SVGに `role="img"`、`title`、`desc`、`figcaption` を付ける。`desc` は絵を見ない読者が同じ内容を追える文章にする。
- markerは最初のSVGで定義し、同じ文書内の後続SVGから参照する。idは文書全体で重複させない。
- 描いた後に、textのbbox同士の重なり、囲みrectからのはみ出し、viewBox外を機械検査し、0にしてから目視する。検査方法は `validation.md` に置く。

## template側の部品

`assets/editorial-document.html` には次のcomponentを用意している。

- `.analogy`: 「たとえるなら」と `.limit`（比喩の限界）。
- `.caution`: 境界や法的な注意を置く囲み。
- `.step-list`: 代表ケースを番号つきで追う一覧。
- `.qa`: 自己テストの問いと、`details` で折りたたんだ答え。
- `.scene`: 場面の絵に使うSVGの文字設定。

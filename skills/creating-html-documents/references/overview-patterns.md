# 全体像の図を、問いに合わせて設計する

全体像の図（overview）の形を、題材と読者の問いから決めるための手順と型を定める。決まった形の図に題材を流し込まない。番号の箱を縦に並べ、範囲と失敗の箱を横に添える形は、どの題材にも合うように見えて、どの題材のドメインも見せない。

## 1. 図の問いを一文で決める

描く前に、読者がこの図を一目見て答えられるべき問いを一文で書く。問いが決まらないまま描くと、要素を並べただけの図になる。

- 「この業界には誰がいて、お金と請求書はどう流れ、この文書はどこを扱うか」
- 「注文から入金まで、誰が何をどの順でするか」
- 「この機能は、どの層の上に載っていて、何に頼っているか」
- 「売上目標は、どの数字の掛け算でできているか」
- 「競合は、どの軸で見るとどこにいるか」

問いは図の設計に使う。図の `title` とcaptionの一文目には、その問いへの答えを一文で書く（例: 「掛け払いには5者がいて、お金と請求書は別の道を流れる。この文書は立替払いの部分を扱う」）。

## 2. 部品表を作る

問いに答えるのに要る部品を、描く前に作業メモへ列挙する。HTMLには書き出さない。

```text
図の問い: 読者が一目で答えるべき問い
主体: 名前 / 役割を一文で / 属する領域 / 詳しく扱う章
流れる物: 種類（お金、モノ・サービス、書類・データ、権限、契約など）/ どこからどこへ / いつ
領域: 役割の近い主体のまとまり。この文書が扱う範囲、隣接する領域、範囲外
配置の軸: 横と縦がそれぞれ何を意味するか
省くもの: 今回の問いに答えるのに要らない主体や流れ
```

主体と流れる物は、source inventoryとclaim ledgerにあるものだけにする。数を合わせるために主体を作らない。逆に、本文で扱う主体が図にいなければ、図の問いか部品表を見直す。

## 3. 形を選ぶ

問いの種類から形を選ぶ。一枚の図に二つの問いを詰めない。二つの問いがあるなら図を二枚にし、二枚目は一枚目の一区画を拡大したものとして、同じ名前と番号で接続する。

- ドメイン俯瞰図: 「この領域には誰がいて、何が流れ、対象はどこにいるか」に答える。主体を領域ごとにまとめて配置し、流れる物を線の種類で分け、この文書の範囲を枠で囲む。業界や事業ドメインの解説、市場・競合の調査、事業・戦略の検討で、読者が対象を大きな地図の中に位置づける必要があるときに使う。初学者向けでは場面の絵を既定にし、場面に収まらない主体を見せるときだけ、その前に置く。描き方は下の「4. ドメイン俯瞰図の描き方」に置く。
- 流れ図（スイムレーン）: 「誰が何をどの順でするか」に答える。主体ごとに横のレーンを引き、左から右へ時間が進む。業務フロー、取引の一件の流れ、システム間の処理の順に使う。
- 層の図: 「何の上に何が載り、何に頼っているか」に答える。下の層ほど基盤にし、上の層は下の層だけに頼るように積む。プロダクトの構成、技術スタック、事業を支える仕組みの整理に使う。
- 分解ツリー: 「この数字や目標は、何からできているか」に答える。左に全体、右へ要素へ分け、枝に演算（掛ける、足す）を書く。KPI、売上の式、課題の分解に使う。
- 位置づけの地図: 「どの軸で見ると、それぞれはどこにいるか」に答える。2本の軸に意味のある名前と両端のラベルを付け、主体を点や箱で置く。競合比較、選択肢の比較に使う。軸の位置が根拠のない印象なら使わない。
- 状態遷移図: 「どんな状態があり、何が起きると次へ移るか」に答える。状態を箱に、移る条件を矢印のラベルに書く。請求、審査、契約のライフサイクルに使う。
- 影響マップ: 「ここが壊れる、変わると、どこへ波及するか」に答える。起点を一つ置き、波及先を距離の順に並べる。障害、変更の影響範囲、失敗の伝播が読者の問いそのものであるときだけ使う。
- 時間軸: 「いつ何が起き、どの期間が重なるか」に答える。横に時間、縦に主体や出来事の種類を置く。歴史、制度の変遷、資金の出入りの期間に使う。
- 場面の絵: 初学者向けで、「全体で何が誰から誰へ動くか」を絵で掴ませる。描き方は `illustrated-explainer.md` の「絵の型」に置く。題材が一つの取引の場面に収まらず、業界全体を見せる必要があるなら、場面の絵の前にドメイン俯瞰図を置く。

失敗の経路は、図の問いに失敗が含まれるときだけ描く。「理解しないと何が起きるか」はorientationの文で示し、全体像の図へ失敗の箱を足して補わない。

## 4. ドメイン俯瞰図の描き方

ドメイン俯瞰図は、読者が詳細へ降りる前に持つべき地図である。対象の箱を数個つないだ図ではなく、対象の外側にいる主体と、主体の間を流れる物まで描く。

### 配置

- 配置の軸を先に決め、凡例かcaptionに書く。例: 横は取引の向き（左が買い手側、右が売り手側）、縦は役割の層（上がルールを決める側、中央が取引の当事者、下が基盤を提供する側）。
- 役割の近い主体を領域にまとめ、領域の見出しを左上に置く。領域は薄い面か細い枠で示し、主体の箱より目立たせない。
- 主体は実在する数だけ置く。8〜16程度が読める上限で、超えるなら役割の近い主体を一つの箱にまとめ、内訳は本文の章で扱う。
- 読者自身の立場（自社、自分のチーム、読者が担当する役割）がドメインにいるなら、その主体の箱を薄いaccentの面（`.node.is-self`）にし、「自社」「あなたの担当」のような語のラベルを `.t-self` で箱の中に置く。範囲の枠（面のないinkの太い線）と同じ見た目にしない。

### 流れる物

- 流れる物の種類ごとに線を分ける。種類は4つまでにする。既定の割り当ては、読者が追う主な流れ（決済ならお金）をaccentの実線、モノやサービスをinkの実線、書類やデータをinkの破線、契約や規制のような縛りをmutedの点線とする。題材の主な流れが別の物なら、その物をaccentにする。
- 線のラベルは、何が流れるかを2〜8字で書き、線の脇の余白に置く。線をラベルの上に通さない。
- 双方向の流れは2本の線に分ける。両端に矢印を付けた1本の線にしない。

### 範囲と章

- この文書が扱う範囲を、inkの太い枠（`.scope`）で囲み、枠の内側の角に「この文書の範囲」と書く。accentは主な流れの線に使うので、範囲の枠には使わない。範囲外の主体は破線の箱（`.node.is-outside`）にしてよいが、消さない。図の全体がこの文書の範囲なら枠を描かず、captionに「図の全体がこの文書の範囲」と書く。読者自身の立場の箱は、範囲の内と外のどちらにあってもよい。範囲外にいることが、読者が位置を掴む手がかりになる。
- 各主体または領域に、詳しく扱う章を「3章」のように文字で書く。詳しく扱う章が無い主体には章番号を書かない。SVGの中にリンクを置かない。`role="img"` のSVGの中のリンクは支援技術に届かず、リンクでない章番号と見た目がそろわない。章へ移動する手段は目次と本文のリンクで用意する。
- 本文の章は、図の主体と流れの名前をそのまま使う。図で「立替払い」と書いた流れを、本文で「代払い」と呼ばない。

### 大きさ

ドメイン俯瞰図は本文の欄の全幅に置く。1440x900では図枠の内側が約1040pxなので、`viewBox` の幅を1040前後にする。高さは内容で決め、主体が多いなら縦に伸ばす。文字は主体名17〜18px、補足14px、線のラベル14px、章番号13pxを起点にし、表示倍率を掛けた実寸で12px未満にしない。

## 5. 記号と凡例

- 記号の意味は、図の中の凡例に書く。captionだけに書くと、図を見ながら意味を確かめられない。凡例は図の上端か下端の帯に置き、線の見本と語を並べる。
- 箱や領域の意味を表す略号として、英字一文字の記号（S、F、Aなど）を置かない。範囲なら「この文書の範囲」、失敗なら「払われない場合」のように、意味の分かる語を書く。段階評価のA〜Eのように、それ自体が読者の知る値である文字は略号に当たらない。
- 番号の丸いバッジは、本文や後の図で同じ番号を再利用する場合だけ使う。番号が順序を表すのか、章を表すのか、索引を表すのかを凡例に書く。
- 色だけで意味を伝えない。線の種類（実線、破線、点線）、枠の太さ、語のラベルを併用する。

## 6. 骨格

ドメイン俯瞰図の骨格を示す。配置、領域の数、主体の数、線の向きは題材で変える。この骨格の配置をそのまま使うことを目的にしない。示しているのは、凡例の帯、領域、主体、範囲の枠、流れの線とラベル、章へのリンクの組み方である。CSSクラスは `assets/editorial-document.html` の `.diagram` に定義してある。

## 7. 描いた後に確かめる

- 部品表の主体、流れる物、範囲がすべて図にあり、図にあるものがすべて部品表にある。
- 図の問いに、図だけを見て答えられる。答えられないなら、問いに要らない要素が多すぎるか、要る流れが欠けている。
- 凡例に、図で使ったすべての線の種類、枠、面、番号の意味がある。英字一文字の記号が無い。SVGの中にリンクが無い。
- 本文の章が、図の主体と流れの名前をそのまま使っている。
- 文字の重なり、箱からのはみ出し、viewBox外、線と文字の衝突を `validation.md` の方法で機械検査し、0にしてから目視する。

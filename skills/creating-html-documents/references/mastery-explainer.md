# 理解の穴に気づける解説

読者がわかったつもりで終わらず、自分の理解の穴に気づき、対象を自分の言葉で説明・予測・応用できるようにするための既定を定める。`technical-explainer` に重ねるほか、読者の理解が目的の `change-review` と `research-report` にも重ねる。初学者向けの `illustrated-explainer.md` とは別の条件で働き、両方の条件に当たれば両方を適用する。初学者向けの条件は目的が読者の理解であることを含むので、初学者向けの文書にはこの既定も重ねる。

## 発火条件

次のどれかに当たれば、明示の指示がなくても適用する。

- 依頼が「解説して」「説明して」「教えて」「わかるように」「理解したい」「仕組みを知りたい」の形をしている。
- 読者が、その対象を身につけたい、マスターしたいと述べている。
- PR、設計、ドメイン、障害、ライブラリの挙動を、読者自身が理解するための文書である。

読者の前提知識の有無は問わない。前提知識の無い読者なら、`illustrated-explainer.md` も重ねる。

次には適用しない。

- 採否を決めるための `decision-plan`、チームが差分を確かめて判断するためのレビュー記録、短い確認用HTML、セッションダッシュボード。
- 差分の把握だけを求める文書。`screen-diff` や、APIの差分を見やすく示す `change-review` などが当たる。「差分が視覚的にわかる」のように見やすさを求める「わかる」は、発火の語に数えない。
- 読者が「仕組みはいらない、結論だけ」と明示した場合。

PRの解説は `change-review` の要素（before / after、ファイルごとの差分）を持つが、目的が読者の理解なら、この既定を重ねる。除外するのは、チームが差分を確かめて判断するためのレビュー記録と、差分の把握だけを求める文書である。

適用するかは、文書の目的が「読者の理解」か「判断・記録」かで決める。判断に迷わなかった場合も、読者と目的を `<meta name="reader" content="読者と目的を一文で">` に一文で残す。この既定と初学者向けの既定を重ねるかの判断も、同じmetaに含める。

## 原則

1. 「わかった気がする」を目標にしない。読み終えた読者が何をできるかを、外から確かめられる形で目標にする。
2. 仕組みを組み立てる段を飛ばさない。結論、用語、具体例、仕組み、適用の順に積む。
3. 読者が自分の理解を試す場面を本文に置く。読むだけで終わる構成にしない。
4. 根拠の強さを主張ごとに示す。確かめていないことを、確かめたように書かない。
5. 手間を理由に要素を削らない。ただし、同じ内容の言い換えで分量を増やさない。

## 必ず置く要素

### 1. 読み終えたらできること

冒頭の要約（decision band）の直後、orientationの前に、読後にできるようになることを3〜5個、外から確かめられる動詞で書く。

- 例: 「Xを3文で説明できる」「Yを変えたら何が起きるか予測できる」「よくある誤解Zがなぜ誤りか言える」「確かめていない範囲を挙げられる」。
- 「理解する」「把握する」「イメージをつかむ」では書かない。達成したかを確かめようがない。
- 各項目を、最後の自己テストのどれかの問いと対応させる。

### 2. 仕組みの地図と中心の問い

対象の仕組みを、次の4つで本文に明示する。「メンタルモデル」「本質」などの語で済ませず、中身を書く。

- 要素: 登場する層、部品、主体、状態。
- 役割と持っている情報: それぞれが何をし、何を知っていて、何を知らないか。
- 因果の連鎖: 入力から結果まで、何が何を引き起こすか。分岐の条件。
- 境界: どこまでがこの仕組みで、どこから外か。成り立たなくなる条件。

可能なら、個々の事実をすべて説明し直せる「中心の問い」を一つ立てる。例は「その層は、その情報を知っているか」。各詳細章は、その問いへの答えとして書く。overviewを置く文書では、仕組みの地図で図を描き直さず、overviewの番号と名称を使って本文に書く。overviewを省く小さな文書でも、仕組みの地図は省かず、本文の箇条書きか短い図で示す。置く位置は `document-system.md` のTechnical explainerに従い、最小用語の後、詳細章の前とする。

### 3. 段を飛ばさない説明

- 具体例 → 一般化 → 別の場面への適用、の順にする。抽象から始めない。
- 用語は初出で定義する。同じ概念には、最後まで同じ語を使う。
- 文脈で意味が揺れる語は定義する。比較の基準時点（before がいつを指すか）、版番号と中身の作り、環境（どの機械、どの版で動いたか）など。
- 「なぜ」には仕組みで答える。名前や分類を言い換えただけの説明にしない。
- 前提を置いた箇所は、前提であることを書く。

### 4. 読む前に予想する問い

主要な章の前に、答えを読む前に予想させる問いを2〜4個置く。

- 予想が外れやすい問いを選ぶ。直感と逆の結果や、よくある誤解に当たる問いがよい。
- 答えの位置を正確に示し、本文で必ず回収する。「答えは第N章の終わり」と書いたら、本当にそこへ置く。
- 回収する箇所では、予想が外れた人が何を見落としていたかも書く。

### 5. 根拠の強さのラベル

主張ごとに、次のどれかを付ける。ラベルは色だけでなく文字で示す。

- 確認済み: 作成時に、コード、ログ、文書、実行結果で確かめた。
- 出典の記載: 出典（PR本文、仕様書、記事）にあるが、作成時に再現していない。出典の名前で呼んでよい（例: 「PRの記載」）。
- 推測: 根拠から導いた推論。
- 未確認: 誰も確かめていない、または確かめる手段がまだない。

付けるときは、次を守る。

- 確かめた範囲を書く。どの環境、版、条件、データで確かめたか。「テストが通った」と「その経路を通した」を区別する。
- 確認済みの欄に推測を混ぜない。一文に両方あるなら、文を分ける。
- 引用符は原文どおりのときだけ使う。要約は地の文で書く。
- 一般論と、この対象に当てはまるかを分けて書く。

### 6. わかったつもりの罠

読み終えた直後に頭に残りやすい誤った理解を、5〜8個並べる。

- 形は「誤解 → 実際 → 戻る章」にする。誤解は、読者が本当に持ちそうなものにする。誰も信じない誤解を立てて崩す形にしない。
- 次の型から探す。
  - 量と中身の混同: 大きさが同じなら中身も同じ。
  - 確認範囲の過大評価: CI が緑なら、すべての経路で確かめた。
  - 一般論の誤適用: 一般に危険だから、この対象でも危険。
  - 層の混同: 上流を直せば、下流にも伝わる。
  - 変化の有無の取り違え: 小さくならないなら、何も変わらない。
- 「一般論としては正しい」話を載せるときは、誤解の文をこの対象に限った形で書き、一覧の中で矛盾させない。

### 7. 自己テスト

- 答えは native の `details` / `summary` で折りたたみ、開く前に声に出すか書いて答えるよう促す。答えをすぐ下に並べると目に入り、予想が成り立たない。hover だけで開く形にもしない。
- 問いの種類を混ぜる。
  - 説明: なぜそうなるか。
  - 予測: もし〜を変えたら、何が起きるか。
  - 区別: AとBは何が違うか。
  - 境界: どこで成り立たなくなるか。何が未確認か。
  - 応用: 別の状況では、同じ仕組みがどう働くか。
- 主要な主張ごとに1問以上、目安は8〜12問にする。「読み終えたらできること」の各項目に、対応する問いを置く。
- 各答えに、戻る章へのリンクを付ける。答えの中で新しい事実を初めて出さない。

### 8. 最後の説明チェック

- 何も見ずに、対象を3文前後で説明させる。含めるべき要点（2〜4点）を先に示す。
- 例文は折りたたむ。
- 詰まった要点ごとに、戻る章を示す。

## 作るときの手順

1. claim ledger の各主張に、根拠の強さと確かめた範囲を付ける。確かめられる主張は、書く前に確かめる。
2. 仕組みの地図（要素、役割と持っている情報、因果、境界）と中心の問いを先に決める。
3. 読み終えたらできることを決め、それを確かめる自己テストの問いを先に書く。
4. 自己テストに答えるのに必要な説明が、段を飛ばさずにそろうように本文を書く。
5. 予想の問い、誤解の一覧、最後の説明チェックを置き、答えの位置とリンクを照合する。
6. 独立レビューでは、通常の観点に加えて次を確かめてもらう。事実の誤りと言い過ぎ、根拠ラベルの強さの不一致、確かめた範囲の過大評価、説明なしに出てくる語、時点や用語の揺れ、理解の断絶。指摘は根拠を確かめてから反映し、反証した指摘は理由を残す。

## 避けること

- 冒頭の要約だけで「わかった」と思わせて終わる構成。
- 読者が自分で試す場面が一つも無い構成。
- 答えを問いのすぐ下に見せた自己テスト。
- ラベルの無い言い切りや、確かめた範囲が書かれていない「確認済み」。
- 同じ概念を、章ごとに別の語で呼ぶこと。
- 分量を減らすために、仕組みの段、誤解の一覧、自己テストを省くこと。

## template側の部品

`assets/editorial-document.html` には次のcomponentを用意している。

- `.goals`: 読み終えたらできること。
- `.predict` と `.answer`: 読む前の予想と、その回収。
- `.tag`（`.fact` / `.cited` / `.guess` / `.open`）: 根拠の強さのラベル。
- `.myths`: わかったつもりの罠。
- `.qa` と `details`: 答えを折りたたんだ自己テスト。

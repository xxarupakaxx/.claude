# セッションダッシュボード

各セッションの最初の具体的な依頼で、費用、進捗、タスク、未回答の質問を確認できる自己完結HTMLを作成し、一度開く。通常の局所作業も対象とする。固定テンプレートは使わず、その作業に必要な情報量で構成する。会話だけの挨拶、ユーザーによる表示不要の指定、書込禁止の依頼では作成しない。

## 作成・更新・再開

1. session/thread IDと作業対象を確認する。同じIDで保存済みのHTMLがあれば再利用する。更新時刻だけで別セッションのタスクを選ばない。IDを取得できなければ一意な作業IDを作って会話にpathを残し、再開時はそのpathを使う。
2. runtime homeの`.local/dashboards/<session-id>/dashboard.html`へ保存する。Codexは`~/.codex`、Claudeは`~/.claude`を使い、IDを安全な単一path成分として扱う。外部Vaultの機密入力を含む場合だけ、対象の`.local/secret/`境界へ保存する。会話本文、認証情報、secret referenceをHTMLへ転記しない。
3. 依頼の目的と完了条件を把握した時点で初版を作り、下記の検証後に開く。調査途中は未確定事項を明記し、計画確定まで表示を先送りしない。HTML作成は、調査依頼における対象ソースの変更を許可しない。
4. 計画変更、タスク着手・完了・停止、質問回答、主要検証、最終報告の前に同じHTMLを更新する。毎ツール呼出しで書き換える必要はない。更新時刻と集計時点を表示する。新しいタブを更新のたびに増やさない。
5. 初版の検証後、`python3 ~/.claude/scripts/open-default-browser.py <dashboard.htmlの絶対path>`を実行する。このコマンドはOSのデフォルトブラウザを開く。macOSではLaunch ServicesからHTTPSの既定ブラウザを取得し、検査済みHTMLのfile URLをそのアプリで開く。HTMLファイルの関連付けだけに依存せず、ブラウザ名を固定しない。ユーザーが明示した場合だけブラウザ指定を変える。Claudeのファイル表示・アプリ内ブラウザ・リンク提示だけでは代替しない。起動の終了状態を確認し、失敗なら原因を調べて修正・再実行する。OSの権限やブラウザ不在で開けない場合は未完了として理由を報告し、成功扱いにしない。起動要求の成功と実画面の検証は区別する。静的HTMLは自動更新ではないため、更新後は同じタブの再読込で確認する。
6. 再開時は未完了タスク、依存、未回答の質問、詳細プラン・設計書を確認する。完了後もHTMLを保持する。別sessionで継続する場合は元タスクへの参照を残し、費用は新旧sessionで区別する。

## 画面に載せる内容

薄い背景と白いカード、控えめな罫線を基本とし、上部のサマリー、タスク表、質問表、詳細の順に置く。タスク一覧と阻害要因は初期表示で読めるようにする。数値カードの数や段組みは情報量と画面幅に合わせる。

- 冒頭: 作業名、目的、現在地、次にすること、更新時刻。
- サマリー: 費用（API換算）、対象セッションの費用、キャッシュ読み込み率、ツールエラー率、完了数/全タスク数、未回答数。文脈読み落とし・自動続行等は測定できるときだけ追加する。費用が取れない場合もカードを消さず「未取得」と理由を示す。
- タスク表: 安定したID、状態（todo / doing / blocked / done）、題名、blocker。doingとblockedを先に、todo、doneの順に並べる。状態は色だけで表さない。
- タスクの詳細: 目的、詳細な手順、設計・変更対象、依存タスク、成果物、完了条件、検証結果と根拠。題名から同じHTMLの詳細anchorへ移動できるようにする。長い詳細は折りたためるが、結論とblockerは一覧に残す。
- 設計書・計画書: 既存の正本へリンクし、判断に必要な内容をタスク詳細にも要約する。新規の作業計画は規模によらず、このHTML内の計画全文を正本とする。継続する製品仕様はdocsへ置き、ダッシュボードだけに閉じ込めない。
- 質問表: ID、緊急度、問い、回答待ちの間に進められること、回答が必要な作業。質問ゼロなら「なし」。承認が必要な作業を無回答のまま進める既定値は置かない。

タスクは成果物や判断のまとまりで分解し、単なる一操作やfileごとに増やさない。doneは完了条件と検証根拠が揃った場合だけ付ける。タスク数、状態別件数、質問数を表と一致させる。今回の計画、変更、検証を追跡できればよく、画像の数値や無関係なサンプルタスクは転記しない。

## 計画の正本とレビュー

新しく作る作業計画の正本は、このダッシュボード内の計画全文とする。別の30_plan.htmlや計画Markdownを並行編集しない。製品の継続仕様・ADR・実装・テストは既存の正本を維持し、計画からリンクする。

### 同じ計画を読む

- 全体計画と各タスクの計画本文に安定したanchor、task ID、計画版を付ける。元依頼の要点と出典、目的、前提、対象・対象外、採用案と理由、詳細手順、設計、依存、成果物、完了条件、検証方法と期待結果、判断境界・停止条件を記載する。会話全文は転記しない。
- レビュー担当と実装担当へ、正本HTMLの絶対path、計画anchor、対象task ID、計画版、必要な根拠資料を渡す。サマリーだけで審査・実装せず、対象計画の全文と元依頼を読む。短いbriefは導線として使い、別の計画正本にしない。
- 新しいセッションから同じtaskを継続する場合は、最初に正本となったHTMLのpathとanchorを引き継ぐ。新しいセッションのダッシュボードは自分の費用と参照リンクを持ち、継続taskの計画本文は元の正本だけで更新する。同時編集する担当は一人にする。元taskのhandoverや作業記録に正本の絶対pathとanchorを残し、取得不能・候補複数・同時編集の場合は対象taskを止めて正本を確認する。

### 審査する版を固定する

- 計画本文の領域と、費用・進捗・質問の状態・レビュー結果の領域を分ける。審査前に対象の計画本文と依頼・前提・受入条件を含む全体計画を、版付きの読取用証拠として同じdashboard directoryのreviews/へ保存し、SHA-256と元anchorを記録する。保存済み証拠は上書きしない。証拠は編集用の計画正本ではない。
- 審査記録にはtask ID、計画版、本文証拠のpathとSHA-256、審査担当・実施時点、判定、理由、指摘ID・重要度・対応状態・修正根拠、実際のレビュー出力へのリンクを持たせる。HTML本文を唯一の審査一覧とし、過去の出力は証拠として参照する。
- 依頼・目的・前提・設計・手順・依存・受入条件など計画内容を変えたら版を上げ、影響するレビューを「未審査」に戻す。依存先の計画変更が自taskの前提へ及ぶ場合も対象とする。費用、実行進捗、検証結果、指摘への対応状態だけの更新では計画版を上げない。質問の回答が設計や前提を変える場合は計画変更として扱う。
- 実装開始前と完了判定前に、現行の対象計画と保存済み審査対象本文が一致するか担当者が照合する。版ラベルだけを合わせて本文差分を見落とさない。異なれば実装・完了判定を止め、影響範囲を確認して再審査する。HTML全体のhashは費用更新でも変わるため計画審査の識別に使わない。

### 画面で追う工程

各taskの詳細から、目的確認 → 計画レビュー → 実装 → 検証 → 完了レビューの状態・指摘・対応・根拠を読めるようにする。レビューは「未審査 / 審査中 / 差戻し / 合格 / 対象外」を文字で示す。対象外は既存workflowで独立審査が不要な局所作業に限り、理由を記録する。審査担当が使えないことを対象外や合格の理由にしない。

管理する作業の目的・計画はmakerと独立したcheckerがこの正本を順に審査する。目的が合格してから計画を判定する。未審査、差戻し、本文不一致、未解決の正しさに関わる指摘があれば対象taskの実装を開始しない。完了レビューでは同じ目的・成功場面・受入条件と実際の成果物・検証証拠を照合し、必要な審査と検証が揃ってからdoneにする。通常の局所作業へ固定人数・固定round・大規模審査を一律追加しない。

この運用は担当者が実行する手順であり、ブラウザやOSが実装を自動的に禁止する機能ではない。旧parser、task-context.py --execution、sync-roadmap.pyを新しいHTMLに適用しない。既存の承認・品質条件は維持する。

### 過去の計画を引き継ぐ

過去の30_plan.html、30_plan.md、plan-review.json、80_review.md等は削除せず参照できるようにする。移行時は元path、計画内容、未完了条件、審査と証拠の対応を確認し、ダッシュボード内へ引き継いだ正本path・anchorを明記する。移行前は旧計画を正本として参照し、移行完了後は旧計画を履歴として保持する。移行しただけで旧審査を新しい計画の合格にせず、審査対象との同一性を確認できなければ未審査にする。

## 費用・利用量の取得

対象を明示したローカル記録から、数値と必要な識別子だけを抽出する。生の会話、tool引数・結果全文、認証情報を出力・保存しない。各指標に取得元、対象session/期間、取得時点、完全/部分/未取得を付ける。別セッションの数値を現在のセッションとして表示しない。

### Claude

- `~/.claude/projects/`の該当session JSONLにある`type: cost-state`の最後の有効な`totalCostUSD`を優先する。これは記録済みの累計であり、行ごとに足さない。`hasUnknownModelCost`がtrueなら部分集計とする。レコードがなければ記録額は未取得とし、0と扱わない。モデルとusage内訳があれば下記の日本円表示手順で推定額を別に計算する。
- 複数sessionを集計する場合はsession IDで重複排除し、各sessionの最後の累計だけを合計する。対象範囲と記録あり/全session件数を表示する。親に含まれる子agent費用を再加算しない。親子の包含を確認できない場合は別枠にする。
- 読込不能、途中行、破損JSON、負数・非有限数があれば、その影響を欠測・部分集計として明示する。料金情報のないsessionを黙って除いた値を「全体累計」と呼ばない。
- 累計には過去日が含まれ得る。ファイル更新日で日次費用を算出しない。日次表示には期間境界の記録または期間を指定できる既存集計器が必要。
- tokenはassistant messageのusageをmessage IDで重複排除して集計する。streamingで同じmessage IDが繰り返される場合は最後の完全なusageを使う。入力全体は`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`、キャッシュ率は読み込みtoken/入力全体。既存`cost-state.modelUsage`の累計から得る場合も加算を重ねない。

### Codex

- `~/.codex/sessions/`のsession_metaのIDが一致する記録を読む。`token_usage_record`の最新`thread_token_usage`をセッション累計として使う。ない場合だけ`event_msg/token_count`の最新`info.total_token_usage`を使い、両方を加算しない。累計を行ごとに足さない。
- `cached_input_tokens`は`input_tokens`の内数。キャッシュ率はcached/inputで、分母0は未取得。出力tokenにはreasoningを二重加算しない。
- USD額が記録されていれば取得元と範囲を示して使う。USD記録がなくてもtoken内訳とモデルが分かる場合は、公式単価を確認してAPI換算の推定額を計算し、日本円で表示する。料金区分が不明なら標準料金を仮定した参考額と明記し、確認済みの他区分の額も併記できる。モデル名から単価を推測せず、利用上限の使用率を費用へ換算しない。

### 日本円での表示

- 費用カードは「約¥1,234」のように円換算額を主表示し、元のUSD額と「API換算・推定」または「API換算・記録値の円換算」を添える。token累計も残す。ClaudeでUSD記録がない場合も、モデルとusage内訳から同じ手順で推定する。
- 公式料金表でモデル・料金区分・入力・キャッシュ読み込み・書き込み・出力の単価と適用条件を確認し、出典URLと確認日を保存する。モデルや料金区分が途中で変わった場合は区間別に計算する。現在の単価を過去の利用量に当てる場合は「現在単価での参考額」と明示する。
- 通常入力、キャッシュ読み込み、キャッシュ書き込み、出力をそれぞれの単価で計算し、USD小計を合算する。Codexで書き込みが0なら `(input_tokens - cached_input_tokens) × 入力単価 + cached_input_tokens × キャッシュ単価 + output_tokens × 出力単価` を100万token単価なら1,000,000で割る。書き込みがある場合はusageの包含関係を確認して通常入力との二重計上を避ける。reasoningは出力へ再加算しない。長文割増はセッション累計ではなく呼出しごとの入力長で判断する。
- `円換算額 = USD額 × 1 USDあたりのJPY`。公開為替情報を確認し、レート、基準日、出典URL、取得日を表示する。休日は直近公表日の値を使う。取得不能なら保存済みレートの日時と参考値であることを明記し、保存値もなければUSD額と「円換算待ち」を出す。根拠のない固定レートを使わない。
- 計算途中は丸めず、表示時だけ円単位に四捨五入する。小額は小数や「1円未満」で示し、丸めによる0円を未使用と誤認させない。料金区分やモデル割当てを仮定した場合はカードにもその前提を短く示す。モデルや内訳が不明で計算できない部分は理由と対象範囲を表示し、既知の小計を全体費用と呼ばない。
- API換算はサブスクリプションの実請求額ではない。税・決済手数料・追加ツール料金や別agentの扱いなど、集計対象外を明示する。表示したtokenと金額は同じ集計時点・範囲に揃え、節目で再計算する。

### 共通

費用の表示名は「API換算・記録値」または「API換算・推定」とし、サブスクリプションの請求額とは区別する。通貨を明記する。予算上限はユーザー指定または既存設定がある場合だけ表示し、超過時は超過額も出す。画像の上限値を採用しない。

ツールエラー率は、結果が判明した呼出しのうちエラーだった件数/結果が判明した呼出し件数。ツールが提供するerror flagや終了状態を使い、本文の「error」という単語では判定しない。呼出しと結果を照合できなければ未取得とする。cache率やerror率は分子・分母も示す。文脈読み落としはコンテキスト量減少だけから推測しない。

`post-cost-track.sh`は時刻とツール名だけの記録であり、token・費用の取得元にはならない。ccusage等が導入済みならその仕様・集計範囲を確認して使えるが、表示のためだけに未導入ツールを自動installしたり、生ログを外部送信したりしない。

## 表示と検証

`html-plan` routeの`session-dashboard-authoring`として扱う。固定テンプレート、専用viewer、常設server、同期daemonは不要。headにDOCTYPE、lang、charset、viewport、title、artifact-kind、CSPを持つsemantic HTMLを直接作る。外部ロードと実行scriptは禁止し、数値・文言はHTML escapeする。表、anchor、details/summaryを使い、キーボードで詳細までたどれるようにする。

保存後は静的HTML検査、内部anchor・外部文書のpathの存在、件数・金額・欠測の整合を確認する。初版やlayout変更時はdesktopと狭い画面で本文のはみ出し、キーボード操作、focus、折りたたみ、色の判別を確認する。実行した検査と未確認事項は区別する。画面実装を変えた場合は`rules/ui-fresh-review.md`に従う。

## 旧Roadmapの扱い

新規・再開とも表示はこの方式へ移す。旧`sync-roadmap.py`、generator、Task Hub、workflow MCP、snapshotは自動実行・再登録しない。過去のタスク、計画、設計書、検証記録と旧コードは保持し、必要なものへリンクする。旧ファイルを新規ダッシュボードで上書きしない。

`roadmap` / `explicit-roadmap`とそのsync、parser、機械属性は過去の形式の参照に限る。新規routeは`session-dashboard`で、旧CLIへ渡さない。既存の要件、承認、未完了の審査・検証は引き継ぎ、表示機構の廃止を理由に合格扱いにしない。新しい作業の実装前には目的・範囲・計画・完了条件を確認し、必要な審査と検証を本文や既存の記録へ残す。
